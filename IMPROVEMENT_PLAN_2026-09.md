## 1. Что на самом деле измерил `baseline-2`

Разбор JSON по парам (не по сводке). Шесть дефектов измерения, каждый с доказательством.

### 1.1 Грейдер мёртв во второй раз, и на этот раз это не таймаут

| факт | значение |
|---|---|
| пар с оценками грейдера | 3 из 44 (`x25`, `x26`, `x36`), все частично |
| стадия `grade`, медиана / максимум | 23.4 с / 44.9 с |
| поводок | 90 с, не достигнут ни разу |
| самые быстрые провалы | `x35` 6.2 с, `x39` 6.9 с, `x32` 7.1 с — те же пары, что были загадкой в `HANDOFF.md` §8 |

Механика (`cognivault-ui/app/rag_pipeline.py`):

- 40 кандидатов режутся на `ceil(40/12) = 4` батча и уходят **параллельно** через
  `asyncio.gather` (`grade`, строки ~715–735).
- Каждый батч — `_call(..., max_tokens=1024)` → `llm.complete_json`. В проде
  `CHAT_PROVIDER: kitai`, то есть `kitai.complete_json`: постановка в очередь → опрос →
  `extract_json` над `message.content`. **Повторов при 429/5xx у KitAI-ветки нет**
  (они есть только у прямого GigaChat, `gigachat.py:279`).
- Любое исключение в `_grade_batch` (строки ~660–668) превращается в `log.warning`
  и `[None] * len(batch)`. Дальше `select` при `None` берёт кандидатов **в сыром порядке
  поиска**. Ни SSE, ни `rag_log`, ни отчёт не получают причину.

- `sources[].grade == null` на всех источниках означает, что **все четыре батча** упали:
  успешный батч с пропущенными id даёт не `None`, а `_OMITTED_GRADE = 2`
  (`rag_pipeline.py:670–681`). Отдельный риск этого пути: обрезанный JSON, в котором
  `extract_json` выцарапал первый сбалансированный объект без ключа `grades`, ставит
  **всему батчу двойки** — а это уже ниже порога и `_FALLBACK_GRADE`, то есть дорога к
  ложному отказу с непустым `grades` в логе.
- Ни один провайдер не читает `finish_reason` у скрытых вызовов: `kitai.py:508` его
  отбрасывает, `gigachat._first_choice_text` не смотрит. Обрезку по `max_tokens = 1024`
  (`rag_pipeline.py:655`, захардкожено) постфактум не восстановить.
- `log.info` в UI не виден вообще (корневой логгер на WARNING, `rag_log.py:19–23`), так
  что и второй проход грейдера по порогу 3, и «батч оценён, но фрагменты не упомянуты»
  никуда не пишутся.

Следствие: `context_precision = 0.448`, `keep_top = 1` и порог 4 описывают систему,
которой не было. Это тот же диагноз, что у `baseline` (там причина была в 20-секундном
поводке), но с другой причиной, и она **пока не установлена**. Кандидаты, в порядке
правдоподобия:

1. Модель через KitAI тратит выходной бюджет на скрытые рассуждения, `content` приходит
   пустым/обрезанным, `extract_json` падает. В пользу этого — два факта. Первый: в проде
   `KITAI_MODEL: "glm-5.1"` (`deploy/dropapp/03-configmap-ui.yaml:45`), семейство с
   режимом рассуждений, у которого рассуждения считаются в `max_tokens`. Второй — п. 1.2:
   у основного вызова ответа (бюджет 4096) тот же симптом «долго работала, ничего не
   отдала, стоп по лимиту».
2. Очередь KitAI отвергает четыре параллельные постановки (`KITAI_EMPTY_RESULT` /
   `KitaiQueryFailed`); повторов у KitAI-ветки нет.
3. Ошибка транспорта/HTTP на постановке или опросе.

Проверка занимает минуты и не требует кода: `kubectl logs <ui-pod> | grep "grader:"` —
в предупреждении есть тип исключения, а у KitAI рядом строка с `query_id`. Это первый
пункт плана.

### 1.2 Четыре пустых ответа с `finish_reason = length`

| пара | корзина | stream, с | как посчитано в отчёте |
|---|---|---:|---|
| `x07` | ловушка | 25.4 | единственный «провал» `refusal_ok` — на деле пустая строка |
| `x25` | отвечаемая, cross_lingual | 27.2 | `answer_relevancy = 0`, faithfulness не считался |
| `x31` | отвечаемая, process | 25.0 | `answer_relevancy = 0` |
| `fb25` | отвечаемая, перечисление | 31.6 | `answer_relevancy = 0` |

`event_order = [meta, sources, done]` — ни одного токена, при этом модель работала
25–32 секунды и завершилась по лимиту `max_tokens = 4096`. Это не «плохой ответ» и не
«отказ»: это сбой генерации, который продукт показал пользователю как пустое сообщение,
а харнес засчитал как ноль качества. Пятая пара с `length` (`x05`, 4976 символов) —
обрезанный, но непустой ответ.

Такой симптом (долгая работа, нулевой видимый вывод, стоп по лимиту) — подпись модели,
чей скрытый вывод считается в `max_tokens`; для `glm-5.1` режим рассуждений включён по
умолчанию. `gigachat.stream_chat` и `kitai._extract` читают только `content`; если
платформа отдаёт рассуждения отдельным полем, оно теряется вместе с бюджетом. Это нужно
подтвердить по сырому ответу платформы и по `usage` (Волна A, п. A1).

### 1.3 Судья видит треть контекста

`tools/eval/metrics.py:369` — `format_context(max_chars=4000)` режет **каждый блок** до
4000 символов для всех трёх судейских метрик. Модель при этом видела блоки до 6000
(`file_full_chars`) и до 12000 (`section_max_chars`) символов. В контексте прогона 129
блоков из 216 имеют глубину `file` или `section`, то есть потенциально длиннее капа.

Два доказанных ложных нуля:

- `x18` «колонки `fincert_feeds.feeds_all_view`»: ответ воспроизводит все пять колонок с
  типами и nullable ровно по эталону, со ссылкой `[Источник 1]`. Судья: «контекст не
  содержит информации о таблице» → `faithfulness = 0`, `context_recall = 0`.
- `x24` «для каких моделей финэффект не рассчитывается»: ответ перечисляет модели по
  эталону. Судья: «в контексте нет упоминания ACQUIRER» → `faithfulness = 0`,
  `context_recall = 0.5`. Это ровно та пара, из-за которой кап уже поднимали с 1500 до
  4000 (комментарий в `format_context`), и её снова не хватило.

Категории `table` (0.734) и `exclusion` (0.000) по faithfulness — артефакт капа.
Средний faithfulness занижен минимум на 0.06 только этими двумя парами.

### 1.5 `answer_relevancy` обнуляет правильные ответы с оговоркой

Судья ставит 0 при `noncommittal: true` независимо от содержания:

- `x02`: ответ открывается «прямого ответа не нашлось», затем дословно излагает оба
  факта эталона (YAFCA и «Связи»). Оценка 1 → 0.
- `x09`: даёт заявку `SD0224921826`, ссылку на репозиторий, контакт. Оценка 3,
  `noncommittal` → 0.
- `fb23`: называет Gallery и GD-витрины и честно говорит, что полного списка нет. → 0.

Это одновременно дефект продукта (промпт поощряет страховочную преамбулу — поле `hedge`
в логе как раз для этого) и дефект метрики (оговорка приравнена к отказу). Средний
`answer_relevancy` 0.757 против 0.917 в `baseline` объясняется в основном этим и пустыми
ответами, а не деградацией.

### 1.6 Отчёт не знает, через какого провайдера шёл ответ

`run_settings.gigachat` в логе хранит `model, temperature, max_tokens,
model_context_tokens` (`rag_log.py:271`) — ключей `provider` и `kitai_model` нет.
KitAI берёт имя модели из `kitai_model` (`kitai.py:96`), а снимок пишет `model`. Отчёт
поэтому утверждает «ответ: модель GigaChat-3-Ultra-preview», тогда как ответы почти
наверняка давал `glm-5.1` через KitAI. Для сравнения прогонов это критичный параметр:
без него нельзя отличить смену модели от смены промпта.
