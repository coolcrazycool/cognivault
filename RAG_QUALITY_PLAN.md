# План повышения качества RAG-ответов CogniVault

> Итог глубокого исследования (аудит кода ×2 + 5 веб-ресёрчей, 2026-07-31).
> Статус: утверждён к разработке. Qdrant **1.16.3** на проме поднимает пользователь —
> задача кода: адаптировать сервисы под 1.16.3 и реализовать волны ниже.

## 0. Контекст и границы

**Система из двух сервисов:**
- `src/` — TypeScript/Fastify бэкенд CogniVault: индексация вольтов (поллер → чанкер →
  EmbeddingsGigaR → Qdrant), поиск (`/api/vault/search/*`), CRUD вольта. SQLite (Drizzle,
  per-user `index.db`) — состояние индексации.
- `cognivault-ui/` — Python/FastAPI чат-UI: RAG-оркестрация (`app/rag.py`), вызов GigaChat
  chat/completions (mTLS, стриминг SSE), Confluence-синк. Dual-mode `local|server`.

**Жёсткие ограничения:**
- Закрытый контур: внешних API нет. Единственная LLM — GigaChat (chat + embeddings, mTLS).
  Библиотеки ставить МОЖНО (Python — через SberOSC PyPI-зеркало, pip.conf; npm — сборка на
  GitHub Actions с интернетом). Веса моделей можно запечь в образ на этапе GH-сборки.
- Qdrant на проме = **1.16.3** (деплоит пользователь; код должен работать и с локальным
  docker-compose — выровнять на ту же версию). Клиент `@qdrant/js-client-rest ^1.17` совместим.
- Тесты только офлайн: vitest (TS), pytest + httpx.MockTransport (Python), `node --check`,
  `python -m compileall`. Живой контур в CI недоступен.
- Прод-манифесты: `cognivault.yaml` (бэкенд+qdrant; там pending-изменение PVC — НЕ откатывать),
  `cognivault-ui.yaml` (UI). Образ UI собирает `.github/workflows/docker-publish-ui.yml` →
  ghcr (public) → прокси SberOSC. Новые ENV-ключи каждой волны вносить в манифесты.
- Конвенции: conventional commits, `pnpm check` (TS), стиль существующего кода. ESM, named
  exports, TypeBox для роутов.

**Зафиксированные решения (не пере-обсуждать):**
- База чанкинга (md-заголовки, 100–500 cl100k-токенов, **overlap 0**, breadcrumb в тексте) —
  правильная, не менять.
- НЕ делать: semantic/late/proposition chunking, RAPTOR, multi-query, step-back, Self-RAG,
  multi-hop, обрезку размерности 2560, коллекцию-на-тенанта, отдельный поисковый движок,
  SQLite FTS5 для лексики (заменено серверным sparse-гибридом благодаря 1.16.3).
- Реранкер и грейдер релевантности — ОДИН механизм (батч-оценка GigaChat шкалой 1–5).
- Родительские секции — в SQLite (полный текст), НЕ в payload Qdrant.
- Конвейер чата: ровно 2 скрытых LLM-вызова (интент+condense; батч-грейдер).

### 0.3 Транзакционность индексации (самый серьёзный дефект)

### 0.4 Пустой результат чанкера ≠ «удалить всё»

### 0.5 mtime/size-претест поллера

- Если mtime И size совпадают с БД — файл не читать (считать неизменённым). Хэш — только

### 0.6 Тримминг истории чата (UI)

### 0.7 Скоры и min_score

### 0.8 Достоверность reindex-job

- Пробрасывать failed-файлы из пайплайна в job (`job.errors[]`, счётчик), финальный статус

**Критерий готовности волны:** все существующие тесты + новые зелёные; `pnpm check`;

## Волна 3 — настоящий гибрид + parent-child + хранение (бэкенд, требует 1.16.3)

### 3.1 Sparse BM25 named vector
- Коллекция пересоздаётся (см. 3.5): `vectors: {dense: {size: dims, distance: Cosine}}`,
  `sparse_vectors: {bm25: {modifier: 'idf'}}`.
- Новый модуль `src/lib/bm25.ts` (чистый TS, без нативных зависимостей):
  - токенизация: lowercase, split по не-буквенно-цифровым, отбрасывать стоп-слова (ru+en
    короткий список), **русские слова → Snowball-стеммер ru** (npm `snowball-stemmers`,
    чистый JS), латиница/цифры/аббревиатуры — как есть (это главная ценность лексики).
  - sparse-вектор: `indices = uint32-хэш токена` (fnv1a/murmur), `values = tf-компонента
    BM25: tf*(k1+1)/(tf + k1*(1 - b + b*len/AVG_LEN))`, k1=1.2, b=0.75, `AVG_LEN=300`
    (константа; IDF доклеит сервер через modifier).
- `pipeline.ts`: upsert каждой точки с обоими векторами (`vector: {dense, bm25}`).
- Запрос: тот же модуль строит sparse из standalone-вопроса (стемминг обязателен и там).

### 3.2 Server-side гибрид через Query API
`SearchService.hybrid` → один `client.query`:
`prefetch: [{query: denseVec, using: 'dense', limit: 40}, {query: sparseVec, using: 'bm25',
limit: 40}], query: {fusion: 'rrf'}, limit, filter (user_id + фасеты)` +
`params: {quantization: {rescore: true, oversampling: 2.0}}`.
Контракт REST-ответа сохранить; `score` = rrf (в UI показывается грейдерская оценка, 0.7).
Semantic-эндпоинт остаётся (dense-only, `using: 'dense'`).

### 3.3 Parent-child
- `chunker.ts`: у каждого чанка `parentId = sha1(path + ' ' + sectionPath)` (H1-секция
  = свой parent). В payload добавить `parent_id`.
- SQLite: новая таблица (миграция Drizzle):
```sql
CREATE TABLE sections (
  parent_id    text PRIMARY KEY,
  path         text NOT NULL,
  section_path text NOT NULL,
  text         text NOT NULL,
  content_hash text NOT NULL,
  updated_at   text NOT NULL
);
CREATE INDEX sections_path_idx ON sections (path);
```
  Заполняется в пайплайне атомарно с успешным upsert (0.3); строки удалённых/изменённых
  файлов чистятся по path.
- REST: `/search/hybrid` получает параметр `group_by_section: bool` — при true бэкенд
  дедуплицирует результаты по `parent_id` (клиентская дедупликация после query; Query API
  group_by — опционально, если поддержано клиентом), и каждому результату добавляет
  `section_text` из SQLite (лимит `section_max_chars`).
- UI `rag.py`: section-slice по имени заголовка (`_slice_section`, F-10) заменить на
  `section_text` из ответа бэкенда. Whole-file расширение (≤6000 chars через `/content`)
  оставить.

### 3.4 Реранкер на 40 кандидатов
UI: `RAG_RERANK_CANDIDATES` → 40 (лимит запроса к `/hybrid`), грейдер 2.2 работает
батчами по 12 параллельно. Изменений кода сверх конфига — минимум.

### 3.5 Конфигурация коллекции + blue-green
- `qdrant.ts` createCollection: quantization `scalar int8 {always_ram: true, quantile: 0.99}`,
  dense `on_disk: true` (оригиналы), `on_disk_payload: true`; user_id-индекс с
  `is_tenant: true`.
- Fingerprint схемы: `fp = sha256(provider|model|dims|chunkerVersion|sparseScheme)[:8]`,
  имя коллекции `cognivault_{fp}`, alias `cognivault` → на неё. При старте: alias есть и
  указывает на коллекцию с тем же fp — ок; иначе создать новую коллекцию, переключить alias
  (старую коллекцию удалить после успешного reindex), залогировать «reindex required».
  Все операции — через alias.
- `chunkerVersion` — константа в коде, инкрементится при изменении логики чанкинга (Волна 4!).

### 3.6 Миграция
Волна требует полной переиндексации (новые векторы/схема). Прод: qdrant на emptyDir —
рестарт пода + `POST /api/admin/reindex` на пользователя (или авто по fingerprint-логике).
Локально: то же через admin API. Задокументировать в плане релиза волны.

**Критерий:** vitest: bm25-модуль (стемминг, латиница нетронута, детерминизм хэшей);
mock query-вызова (prefetch-структура); дедуп по parent_id + section_text; fingerprint/alias
логика. UI-тесты: rag.py использует section_text. Интеграционно (локально, живой qdrant
1.16.3 в compose): гибрид находит по точному термину («SberOSC», код ошибки), которого

## Волна 4 — таблицы и обогащение чанков (бэкенд + переиндексация)

### 4.1 Table-aware чанкинг (`chunker.ts`)
Сейчас таблицы >500 токенов режутся `splitTextByLines` без шапки — главный режим отказа.
- GFM-таблица в AST: если целиком ≤ бюджета (~1200 cl100k-токенов) — один чанк.
- Иначе row-group чанки: целые строки, ~15–40 строк на чанк до ~1200 токенов, в КАЖДОМ:
  контекст-префикс (`{title} > {section_path} > Таблица: {подпись/первый абзац перед ней}`)
  + строка заголовков + разделитель + строки. Строку не рвать никогда.
- Payload: `content_kind: 'table_rows'` (обычные чанки — `'text'`, k5 миграция payload).

### 4.2 Summary-чанк таблицы
Для таблиц, порезанных на группы (т.е. больших):
- Новый модуль `src/lib/gigachat-chat.ts` — минимальный chat/completions-клиент на
  инфраструктуре mTLS из `gigachat-embedding.ts` (без стриминга, 1 промпт → текст).
- Промпт: «Опиши таблицу 1–2 предложениями: о чём она, перечисли колонки и по 1–2 примера
  значений» (вход: шапка + первые ~10 строк).
- Отдельная точка: `content_kind: 'table_summary'`, `parent_id` таблицы; текст = summary.
  Попадание в retrieval → UI получает section_text (вся таблица, кап по бюджету).
- Флаг `INDEX_TABLE_SUMMARY` (default true), сбой вызова — нефатален (skip + warn).

### 4.3 Doc-summary в каждый чанк
- Тот же `gigachat-chat.ts`: 1 вызов на документ — «Аннотация 1–2 предложения: о чём документ».
- Кэш в SQLite `doc_summaries(path PK, content_hash, summary)` — пересчитывать только при
  смене hash (переживает reindex, т.к. /data бэкенда на PVC).
- Текст чанка при эмбеддинге и в payload: `Аннотация документа: {summary}\n\n{текст чанка}`.
- Флаг `INDEX_DOC_SUMMARY` (default true). Сбой — нефатален (чанк без аннотации).
- Оценка стоимости индексации: 1 вызов Lite/документ — копейки; логировать счётчик вызовов.

### 4.4 Мелочи чанкинга
- Хвостовые секции <100 токенов гарантированно склеиваются (проверить sectionsToChunks на
  хвосте документа, покрыть тестом).
- Canvas/Excalidraw: верхний лимит чанка 500 токенов — длинные узлы резать по абзацам.

### 4.5 Согласование конвертера Confluence (UI)
- Порог разбиения таблиц в `convert.py` (~350 токенов с повтором шапки) поднять до ~1200 —
  согласованно с 4.1, чтобы конвертер и чанкер не резали двойным швом; кап на суммарный
  размер развёрнутой merged-cell таблицы (страницы >1MB — причина прошлых 413).
- Убрать `\[`-экранирование markdownify в status-макросах (косметика из бэклога).

### 4.6 `chunkerVersion++` → fingerprint-механика 3.5 сама потребует новую коллекцию + reindex.

**Критерий:** golden-тесты чанкера: большая таблица → группы с шапкой и префиксом; строки
целы; summary-чанк присутствует (мок chat-клиента); doc-summary кэшируется по hash. E2e
локально: агрегатный вопрос по большой таблице находит table_summary → в контексте вся таблица.

## Волна 5 — оценка качества (параллельно, начать ДО волн 3–4 для замера дельты)

### 5.1 Логирование запросов (UI)
Per-user JSONL (`{data}/rag_log.jsonl`, ротация): ts, intent, raw/standalone question,
кандидаты (path, chunk_index, rrf-score), grades, финальные источники, длина ответа,
невалидные цитаты (1.3). Секреты не логировать.

### 5.2 Golden-set
`tools/eval/` (репо): скрипт генерации Q&A из чанков корпуса через GigaChat
(промпт: 1 фактологический + 1 практический вопрос на фрагмент, ground_truth строго по
фрагменту; JSON) + формат ручной валидации (accept/reject поле). Цель: 50–100 пар.

### 5.3 Eval-harness
`tools/eval/run.py`: гоняет golden-set через живой локальный стек (UI API), считает
метрики через **gigaragas** (`faithfulness_ru`, `answer_relevancy_ru`, context
precision/recall; русский сегментатор предложений вместо NLTK-дефолта). Отчёт markdown +
JSON. A/B: два прогона с разными конфигами → diff-таблица. Абсолютным цифрам судьи не
доверять — только относительным (A/B, тренд).
Зависимости — через SberOSC PyPI (проверить доступность gigaragas в зеркале; если нет —
вендорить только нужные промпты/метрики, они MIT).

### 5.4 Обратная связь в UI
Кнопки 👍/👎 под ответом → в лог 5.1. (Минимальный HTML/JS, без БД.)

**Критерий:** baseline-отчёт на текущем main ДО Волны 3; отчёт после каждой волны 3/4;
правило диагностики: нужный чанк был в контексте + ответ неверен → чинить генерацию,
не был → ретрив.
